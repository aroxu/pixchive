# 개발 및 실행

Python 3.14, uv, Node 24와 npm이 필요하다. 정확한 Python/JS 의존성은 `uv.lock`과 `frontend/package-lock.json`에 고정되어 있다.

## 로컬 실행

저장소 루트에서 실행한다.

여러 주소를 같은 서비스에 사용할 때는 `PIXCHIVE_ALLOWED_ORIGINS`에 완전한 HTTP/HTTPS Origin을 쉼표로 구분해 지정한다. 기본 `PIXCHIVE_PUBLIC_URL`도 항상 허용하며 추가 목록은 프로토콜·호스트·포트를 정확히 비교한다. `.env`는 Compose가 자동으로 읽으며 로컬 실행에서는 먼저 환경 변수로 불러온다.

```sh
set -a
. ./.env
set +a
```

현재 로컬 `.env`는 요청한 `localhost`, `archive-server`, `archive-server.example.net`의 기본 HTTP/HTTPS 포트와 8000번 포트만 추가로 허용한다. 다른 포트/호스트를 쓰면 해당 Origin을 명시적으로 추가한다. 로그인과 CSRF 검사는 그대로 적용하며 HTTPS 주소에서 로그인한 세션에는 Secure 쿠키를 사용한다. `.env`는 이미지 빌드와 버전 관리에서 제외한다.

```sh
uv sync --frozen
npm --prefix frontend ci
npm --prefix frontend run build
uv run python -m app.cli init
PIXCHIVE_REDIS_URL=redis://127.0.0.1:16379/0 uv run uvicorn app.main:app --host "${PIXCHIVE_BIND_HOST:-0.0.0.0}" --port 8000
```

`http://localhost:8000`을 연다. 초기 설정 키는 `secrets/setup-token`에 생성되며 초기 관리자 생성 이후에는 사용할 수 없다. 키 파일은 사용자가 읽어 입력한다. 비밀번호를 코드·명령행 인자에 넣지 않는다.

`init`은 기존 암호화 키나 DB를 덮어쓰지 않는다. `secrets/credential.key`와 `secrets/setup-token`은 0600 권한으로 생성된다. `data/`와 `secrets/`는 버전 관리에서 제외한다.

합성 샘플이 필요한 개발 환경에서만 별도 실행한다. 시작할 때 자동 삽입하지 않는다.

```sh
uv run python -m app.cli seed-fixtures
```

6개 작품·8개 페이지가 생성된다. 화면에 `샘플`로 표시하고 Pixiv 원본 링크는 제공하지 않는다. Pixiv 계정이나 네트워크를 사용하지 않는다.

UI 개발 서버를 사용할 때는 API의 Origin 설정도 맞춰야 한다. API와 Vite를 각각 실행한다.

```sh
PIXCHIVE_PUBLIC_URL=http://localhost:5173 PIXCHIVE_REDIS_URL=redis://127.0.0.1:16379/0 uv run uvicorn app.main:app --host "${PIXCHIVE_BIND_HOST:-0.0.0.0}" --port 8000
npm --prefix frontend run dev
```

이때 브라우저 주소는 `http://localhost:5173`이다. `localhost`와 `127.0.0.1`은 다른 Origin이므로 섞어 사용하지 않는다. Vite가 5173을 사용하지 못하면 지정한 포트와 `PIXCHIVE_PUBLIC_URL`을 함께 변경한다.

로컬 worker에는 별도 Redis가 필요하다. 개발용 Compose는 Redis만 시작하며 다른 서비스와 충돌하지 않도록 루프백의 16379 포트를 사용한다. web과 worker에 같은 Redis URL을 설정한다.

우고이라 변환에는 `ffmpeg`와 `ffprobe`가 PATH에 있어야 한다. Docker 이미지는 둘을 포함한다. 로컬 설치는 운영체제 패키지 관리자로 FFmpeg를 설치한다.

```sh
docker compose -p pixchive-dev -f compose.dev.yml up -d --wait
PIXCHIVE_REDIS_URL=redis://127.0.0.1:16379/0 uv run arq app.worker.WorkerSettings
```

worker는 별도 터미널에서 계속 실행한다. 개발용 Redis를 정지할 때는 `docker compose -p pixchive-dev -f compose.dev.yml down`을 사용한다. DB에 남은 작업은 다시 시작하면 회수한다.

## Docker Compose

```sh
mkdir -p secrets
docker compose build
docker compose -f docker-compose.yml -f compose.init.yml run --rm --no-deps web python -m app.cli init
docker compose up -d --no-build
```

`compose.init.yml`은 초기 키 생성 때만 secret 경로의 쓰기를 허용한다. 평상시 web과 worker는 읽기 전용 마운트를 사용한다. 초기 키를 읽으려면 사용자 터미널에서 다음을 실행한다.

```sh
docker compose exec web cat /run/pixchive-secrets/setup-token
```

기본 웹 수신 주소는 `0.0.0.0:8000`이며 로컬 접속 URL은 `http://localhost:8000`이다. 로컬 실행·Compose는 `PIXCHIVE_BIND_HOST`로 수신 인터페이스를 바꿀 수 있다. 다른 포트는 `PIXCHIVE_PORT`와 `PIXCHIVE_PUBLIC_URL`을 함께 설정한다. 예를 들어 8080을 사용할 때는 두 값을 각각 `8080`, `http://localhost:8080`으로 둔다. 다른 기기에서 접속할 때는 실제 접속 Origin(`http://서버주소:8000` 등)을 `PIXCHIVE_PUBLIC_URL` 또는 `PIXCHIVE_ALLOWED_ORIGINS`에 등록해야 로그인과 저장 요청이 허용된다. 수신 주소 `0.0.0.0`은 브라우저 접속 주소로 쓰지 않는다.

DB·원본은 Compose의 `pixchive-data` 볼륨, 암호화 키는 호스트의 `./secrets` 디렉터리다. WAL DB는 로컬 파일시스템에 두고 NFS/SMB에 놓지 않는다. LAN/외부 제공 시 실제 HTTPS reverse proxy Origin으로 설정한다. `https://` Origin이면 세션 쿠키에 Secure를 설정한다. Redis 포트는 호스트로 공개하지 않는다.

Docker의 기본 bridge가 없는 이 개발 호스트에서는 기본 build가 `network bridge not found`로 실패했다. 전역 Docker 설정을 변경하지 않고 다음 명령으로 이미지를 검증했다.

```sh
docker build --network=host -t pixchive:local .
```

이 우회는 빌드에만 적용된다. Compose 실행은 별도의 일반 bridge 네트워크로 검증했다.

### GHCR 배포

공용 web/worker 이미지는 `ghcr.io/aroxu/pixchive`에 게시한다. `.env`의
`PIXCHIVE_IMAGE`로 `latest` 또는 `sha-<전체 커밋 SHA>` 태그/다이제스트를 지정할
수 있다. 현재 빌드 대상은 `linux/amd64`이며 다른 아키텍처는 검증하지 않았다.
GHCR 패키지가 비공개라면 먼저 `docker login ghcr.io`로 인증한다.

```sh
docker compose pull
docker compose -f docker-compose.yml -f compose.init.yml run --rm --no-deps --no-build web python -m app.cli init
docker compose up -d --no-build
```

`init`은 새 설치 준비용이다. 기존 환경은 데이터·키·설정을 유지하고 업데이트
전에 [운영 안내](operations.md)의 백업 절차를 수행한다. 위 명령은 다운로드한
이미지로 시작하며 로컬의 `build: .` 설정을 실행하지 않는다.

`.github/workflows/publish-image.yml`은 main의 변경/수동 실행에서 자동 테스트와
정적 검사·프런트엔드 build·OpenAPI 일치를 확인한 뒤 GHCR에 게시한다. PR은
검증만 실행한다. 게시 job의 `GITHUB_TOKEN`에만 `packages: write`를 주며
별도 PAT를 저장하지 않는다. 프로젝트 MIT 라이선스와 외부 패키지 라이선스는
이미지에 포함하고 `npm --prefix frontend run licenses`로 프런트엔드 배포본의
라이선스 안내를 생성한다.

## 첫 설정

최초 관리자 생성 화면은 일러스트·만화·우고이라 지원과 소설 미지원을 안내한다. 관리자를 생성하면 `/setup`의 **첫 보관 준비하기**에서 저장 공간 확인 → Pixiv 쿠키 연결/검증 → 다운로드할 작품 등급 → 공개/비공개 범위 선택과 첫 수집 순서로 준비한다. 우고이라는 원본 ZIP과 타이밍을 보존하며 재생 파일은 GIF 대신 x264 H.264 MP4로 만든다.

실제 쿠키는 나중에 등록해도 된다. **라이브러리**로 나간 뒤 설정의 **첫 설정 안내**에서 돌아올 수 있다. 쿠키 저장만으로 연결 완료가 되지는 않으며 별도 연결 검증이 필요하다. 저장된 다운로드 등급을 확인하기 전, 등급 변경을 저장하지 않은 동안에는 안내 화면의 수집 버튼을 사용할 수 없다. 모든 등급을 해제해 저장하면 메타데이터만 수집한다. 화면 방문만으로 Pixiv 요청이나 수집 작업을 시작하지 않는다. 이 안내 화면의 기능·브라우저 검증은 일괄 검증 대기다.

## Pixiv 연결과 수집

설정에서 `PHPSESSID` 쿠키 값을 보관한 뒤 **연결 검증**을 실행한다. 이 요청은 202와 작업 ID를 반환하며 worker가 연결·계정 ID를 확인한다. 브라우저의 Pixiv 로그인 세션 쿠키를 사용한다. 2026-10-10 실제 계정 연결·대표 수집/변환을 확인했으며 전체 수집·만료·요청 제한 등의 검증 경계는 [연동 PoC](pixiv-poc.md)에 있다. 앱은 Pixiv 비밀번호를 받지 않는다.

쿠키는 Pixiv에 로그인한 브라우저의 개발자 도구 → Application/Storage → Cookies → `https://www.pixiv.net`에서 `PHPSESSID`의 **Value만** 복사한다. 전체 Cookie 헤더, `PHPSESSID=` 접두어, 다른 쿠키를 붙이지 않는다. 값은 마스킹 입력되며 API 응답에 반환하지 않는다. 만료되면 Pixiv에서 로그인한 뒤 새 값을 등록한다.

스키마 v3는 기존 refresh token을 `cookie_required` 상태로 분리하며 값을 쿠키로 보내지 않는다. 새 쿠키를 저장하면 기존 자격 증명을 교체하고 연결 검증을 다시 요구한다. 이전 App API 커서는 웹 offset 커서와 호환되지 않으므로 미완료 스캔의 커서를 초기화한다. 작품·원본·완료 다운로드와 로컬 편집은 유지한다. 업그레이드 시 기존 web과 worker를 모두 정지한 뒤 새 버전을 시작한다.

연결 확인 후 공개·비공개·두 범위와 수집 방식을 선택해 **북마크 수집**을 실행한다. 작업 화면에서 단계, 발견·신규·변경·재확인·최신 유지·접근 불가·제외 건수, 처리 파일 수, 항목별 실패와 재시도를 확인한다. 전체 개수를 모르는 동안 진행률을 만들지 않는다. 인증 만료·저장 공간 부족은 대기 상태로 남는다. 쿠키 삭제/교체는 실행 중인 네트워크 수집을 중단하며 이미 보관한 자료에는 영향이 없다. 다른 Pixiv 계정으로 바꾸는 것은 현재 지원하지 않는다.

## 동기화 방식과 예약

**일반 동기화**는 북마크 목록 전체를 확인하고 새 작품, 목록 행이 바뀐 작품, 보관이 끝나지 않은 작품, 정보 갱신 기준이 지난 작품의 상세만 다시 받는다. 목록에서 바로 알 수 있는 북마크 태그·공개 범위·확인 시각은 모든 작품에 반영한다. **전체 메타데이터 갱신**은 모든 작품의 상세를 다시 받는다. 원본 URL과 로컬 파일이 그대로면 다시 내려받지 않는다. 원격에서 접근할 수 없는 작품은 실패와 구분해 `접근 불가`로 집계하고 로컬 보관분을 유지한다.

설정의 **예약 동기화**에서 실행 간격·범위·전체 갱신 주기·작품 정보 갱신 기준·Pixiv 요청 간격을 정한다. worker가 실행 중일 때만 동작한다. 같은 범위와 요구 방식을 충족하는 진행/대기/일시정지 작업에 합치며 다른 범위나 전체 갱신 요청은 순서대로 실행한다. 전체 작업에 일반 요청을 합칠 수 있지만 일반 작업으로 전체 요청을 대신하지 않는다. 연결 검증이 성공하면 인증 대기 중인 수집 작업이 다시 대기열에 들어간다. 요청량 추정과 장애 대응은 [운영 안내](operations.md)에 있다.

**전체 갱신 기준 시각**은 저장된 예약 범위의 메타데이터 완료 기록이다. 공개/비공개 시각을 따로 표시하며 두 범위에서는 더 오래된 시각을 쓴다. 한 범위 기록이 없거나 예전 공통 시각만 있으면 완료를 추정하지 않는다. 목록 확인과 정보 기록을 마쳐도 원본 다운로드/MP4 변환은 진행 중일 수 있다. 정보/북마크 태그 확인 오류가 있는 범위는 시각을 갱신하지 않는다. 범위별 예약/작업 합침 변경의 기능 검증은 일괄 검증 대기다.

작가 프로필 이미지는 목록에서 받은 주소로 로컬에 저장해 작가 목록과 상세에 표시한다. 일반 이미지의 첫 페이지는 받을 때 목록용 WebP 미리보기를 만든다. 이전에 받은 원본의 미리보기는 **보관 파일 검사**가 끝날 때 채운다. 원본은 바꾸지 않는다.

우고이라는 ZIP·프레임 타이밍을 원본으로 보관하고 별도 작업으로 썸네일과 MP4를 만든다. 변환에 실패해도 원본은 유지되며 상세의 **재생 파일 생성** 또는 작업의 **다시 시도**로 로컬 원본에서 재생성한다. 원본 ZIP·타이밍 다운로드에도 로그인과 작품 등급 제한이 적용된다.

현재 한 파일 다운로드 한도는 100 MiB다. 우고이라는 최대 5,000프레임, 총 10분, ZIP 해제 크기 1 GiB, 프레임 파일 20 MiB, 단일 프레임 2,500만 픽셀·합계 5억 픽셀로 제한한다. 변환은 최대 10분·출력 200 MiB이며 한도를 넘으면 명시적 오류로 남긴다. 취득한 ZIP은 그대로 보존하지만 원격 ZIP의 품질이 Pixiv 개별 최고 해상도 프레임과 같은지는 실계정 PoC에서 확인해야 한다. MP4는 마지막 프레임 표시를 위한 1ms 추가 종료 프레임을 포함할 수 있다.

작업 재개가 기존 작업에 합쳐지면 **해당 작업 보기**에서 이어서 확인한다. 받아들인 부모 재개/재시도는 멈춘 변환도 재개하고 새 활성 변환을 실제 연결 작업으로 사용한다. 공유 변환은 다른 진행 부모가 필요한 동안 유지하며 멈춘 다른 부모의 변환은 취소 대신 보존한다. 자신이 중단한 변환은 실제 종료를 기다린다. 명시적 부모 재시도는 취소된 변환을 새 작업으로 요청하되 원본/이전 작업 기록을 유지하고 로컬 삭제를 존중한다. 이 후속 동작의 기능/브라우저 검증은 대기다.

일러스트·만화 상세의 **미리보기 다시 생성**은 보관한 첫 페이지 원본에서 독립 작업으로 목록용 WebP를 만든다. Pixiv 인증/다운로드 등급과 독립적이며 앱 표시 권한을 적용한다. 상태·작업 링크를 표시하고 완료 후 파일/목록을 다시 읽는다. 원본이 없거나 손상되면 먼저 원본 복구가 필요하다. 스키마 v10은 원본별 미리보기 연결을 보존하며 과거 미기록 관계는 실제 생성/보관 검사에서 채운다. 보관 검사에서 보완 실패를 문제/partial로 남긴다. 새 기능·업그레이드/복원·브라우저 검증은 대기다.

## 라이브러리 탐색과 로컬 정리

검색창은 제목·작가 현재/과거 이름·별칭·작품/작가 ID·태그 원문/번역을 찾는다. 공백으로 나눈 단어는 모두 일치해야 하고, `"분위기 참고"`처럼 따옴표로 구문을 묶을 수 있다. 캡션과 메모 본문은 검색 대상이 아니다.

데스크톱의 필터 영역 또는 모바일의 **필터**에서 포함/제외 태그를 하나씩 추가하고 **필터 적용**을 누른다. 포함 태그는 모두 포함(AND)/하나 이상(OR)을 선택한다. 태그 이름은 정확히 일치해야 하며 태그 출처 선택은 포함·제외에 함께 적용된다. 자유 검색의 제목/작가 이름까지 출처로 제한하지 않는다. 다른 유형·등급·공개 범위·보관/원격/북마크 상태·날짜 조건은 AND로 결합한다. 날짜는 UTC 기준, 종료일 포함이며 날짜 미제공 작품은 제외된다. 숨긴 등급은 설정에서 표시를 허용하기 전까지 검색 결과에도 나오지 않는다.

필터·정렬·페이지당 수·카드 크기를 URL로 공유/새로고침할 수 있다. 상세의 **이전 작품/다음 작품**은 같은 검색 결과를 따라 목록 페이지 경계를 넘어 이동한다. **라이브러리로 돌아가기**와 브라우저 뒤로 가기는 목록 위치와 카드 focus를 복원한다. 작품 내 **이전/다음** 버튼은 작품의 페이지를 바꾼다.

**크게 보기**에서는 +/− 버튼·키로 100~400% 확대/축소하고 확대 상태에서 드래그로 이동한다. 화면 맞춤 상태에서는 좌우 스와이프 또는 방향키로 페이지를 바꾼다. `0`은 맞추기, Escape는 닫기다. 실제 터치 기기 호환성은 추가 검증이 필요하다.

모바일 상세에서는 제목·작가·보관/우고이라 변환 상태를 항상 볼 수 있다. **설명·태그·보관 기록 펼치기**를 누르면 태그 편집·메모/별칭·수집 정보·이력/파일 목록·원본 복구/내보내기/삭제를 사용할 수 있다. 접었다 펴도 같은 작품의 입력 초안과 이력/파일 페이지를 유지한다. 접힌 동안에는 이력/파일의 주기적 조회를 멈추며 데스크톱에서는 정보가 항상 펼쳐진다. 열려 있던 삭제 확인창은 너비 변경으로 숨기지 않는다. 이 후속 모바일 동작의 기능·브라우저 검증은 일괄 검증 대기다.

작품 상세에서 메모와 작가 별칭을 저장하거나 빈 값으로 지울 수 있다. 재수집은 이 값을 덮어쓰지 않는다. 작가 목록에서 별칭으로 검색하고, 태그 목록에서는 출처를 유지한 작품 목록으로 이동한다. 라이브러리·작가/태그 작품 목록의 체크박스 또는 **현재 페이지 N개 선택**으로 표시 작품을 선택해 로컬 태그를 일괄 추가/제거한다. 전체 검색 결과를 한꺼번에 선택하지 않으며 페이지나 검색/범위를 바꾸면 선택이 풀린다. 처리 중에는 선택과 입력을 잠그며 결과를 알려 준다. 태그 제거는 원격 작품/북마크 태그를 지우지 않고, 없는 이름을 제거해도 새 사전 항목을 만들지 않는다. 이 후속 선택/편집 흐름의 기능·브라우저 검증은 일괄 검증 대기다.

상세에는 북마크 공개 범위·확인 상태·처음 발견/마지막 확인 시각, 작가의 이전 이름, 다시 받은 원격 정보의 변경 이력이 표시된다. **파일·정보 내보내기**는 원본과 `metadata.json`을 ZIP으로 받는다. **로컬에서 삭제**는 파일 수·용량을 확인한 뒤 보관 파일을 영구 삭제하고 수집 제외 목록에 남긴다. 설정의 **수집 제외 목록**에서 제외를 해제하거나 다시 받기를 실행한다.

설정의 **다운로드할 작품 등급**에서 전체 연령·R-18·R-18G·미확인을 따로 선택한다. 기본 다운로드는 모든 등급이고 표시 기본값은 전체 연령이다. 선택하지 않은 등급도 작품 정보는 수집한다. 아무 등급도 선택하지 않으면 메타데이터만 받는다. 기존 파일은 유지하며 새 선택은 이후 다운로드부터 적용한다.

태그 화면에서 빈 로컬 태그를 만들고 연필 버튼으로 이름을 바꾼다. 같은 이름이 있으면 기존 태그로 로컬 관계만 합친다. 원격 작품/북마크 태그나 Pixiv 번역과 공유된 이름은 변경할 수 없다. 작품 상세의 **원본 확인 및 다시 받기**는 Pixiv 연결 후 현재 원본만 복구하는 작업을 등록한다. **보관 파일 검사**의 문제 목록에는 파일 역할과 누락·손상·읽기 실패를 표시한다.

작가 목록은 현재/과거 이름·별칭으로, 태그 목록은 원문·제공된 번역으로 검색할 수 있다. 목록·작품 상세의 작가/태그 이름을 누르면 `/artists/:id`, `/tags/:id`에서 작품을 탐색한다. 작가 상세는 별칭 편집과 이름 확인 이력을, 태그 상세는 번역 언어/출처와 출처별 작품 수를 표시한다. 같은 작품에 여러 태그 출처가 있어도 전체 수는 한 번만 센다. 상세의 필터 초기화는 해당 작가/태그 범위를 유지하며 작품을 열었다 돌아오면 목록 URL·페이지·스크롤/focus를 복원한다.

작업 목록은 종류·상태·직접/예약 실행으로 필터링하고 과거 이력을 페이지별로 찾아볼 수 있다. 작업을 누르면 `/jobs/:id`에서 다운로드 항목의 대기·완료·실패·등급 제외, 연결된 부모/변환 작업, 문제 항목과 전체 상태 변경을 페이지별로 표시한다. 수집·검증·복구 결과 링크는 등록한 작업으로 이동한다. 설정의 **우고이라 영상 변환**에서 동시 실행 수를 1~2개로 정한다. 기본은 1개이며 변경은 새로 시작할 변환에 적용한다. 보관 검사는 파일을 최대 200행씩 순회하고 정확한 처리 총수는 원본 검사가 끝난 뒤 표시한다.

작품 상세의 **수집한 작품 정보**에서 게시 시각·처음 수집한 시각·수집 당시 작가 이름·계정명·등급 원문 기록을 구별해 확인한다. 작가 계정명은 제공되는 경우에만 보관하며 작가 목록/작품 검색에 포함한다. **보관 파일과 이전 보관본**은 이전 리비전까지 파일 종류별로 페이지 조회하고 크기·해상도·최근 확인 상태·수집 경로·해시를 보여 준다. 확인 완료 상태의 각 파일을 내려받을 수 있다. 이전 자료에 없던 원문과 출처는 추정하지 않는다.

메타데이터 내보내기 포맷 v2는 정규화 등급 외 원문/출처, 작가 계정명·Pixiv 링크, 이전/파생 파일의 상대 경로·상태·수집 경로를 포함한다. 작품 ZIP은 현재 페이지 범위의 페이지별 최신 ready 원본과 최신 우고이라 묶음/재생 파일을 포함하며 그 ZIP 안의 파일만 metadata.json에 나열한다.

위 기능은 2026-10-04 구현으로, 기능 테스트와 브라우저 E2E를 일괄 검증 단계에 남겼다.

**원격 변경 이력**은 최근 50개 제한 없이 페이지별로 전체 기록을 조회한다. **당시 정보 보기**에서 제목·설명·작가/계정명·등급 원문·게시/북마크 시각과 당시 작품/북마크 태그·번역을 확인한다. 기록의 시각은 서로 다른 정보 버전을 처음 확인한 시각이며 매번 동기화한 시각이 아니다. 읽기 불가/등급 숨김과 직전 기록 비교 불가를 구별한다. 이전 정보는 열람만 제공하며 로컬 메모/태그를 복원하거나 덮어쓰지 않는다. 스키마 v8은 이력 조회 인덱스만 추가한다.

작품 ZIP 내보내기는 파일 존재/크기를 먼저 확인하고 실제 전송 바이트의 크기·해시를 확인한 후 ZIP을 완료한다. 전송 중 삭제/손상/읽기 오류가 있으면 다운로드를 중단하며 파일을 조용히 생략하지 않는다. 화면 불러오기에 실패하면 수동 새로고침·라이브러리 이동을 제공하며 내부 예외는 표시하지 않는다. 이번 후속 변경의 기능/E2E 검증도 대기 중이다.

작가·태그 목록은 24개씩 서버에서 조회하며 검색·이름순/작품 수순·태그 출처와 페이지를 URL로 유지한다. 작가의 과거 이름/계정명/별칭/ID와 태그의 원문/번역을 검색한다. 태그는 출처별 카드로 표시하고 그 출처의 고유 작품 수를 센다. 표시 등급·수집 제외를 반영하며 실제 미사용 로컬 태그는 0건으로 남는다. 상세와 작품을 열었다 목록으로 돌아오면 조건·스크롤/focus를 복원한다. 이름 변경은 서버에서 같은 이름 여부를 확인한 뒤 저장할 수 있으며 화면 전체 사전을 받지 않는다. 이 변경의 기능 테스트·E2E·대량 자료 성능 측정은 아직 실행하지 않았다.

작업을 시작하기 전에 원본/미리보기/아바타·우고이라 프레임과 MP4/저장 복사본의 예상 공간을 확인한다. 모든 worker가 유효한 작업의 예약을 공유하고 기본 여유 공간을 유지한다. 공간 대기 상태의 작업에는 **필요한 여유 공간 (추정)**·검사 당시 남은 공간·확인 시각을 표시하며 설정은 진행 작업의 공간 예산을 실제 보관 용량과 구별한다. 스키마 v9는 이 마지막 확인 값과 공용 예약 표를 추가하고 종료·중단 확인·lease 만료·백업 복원 때 예약을 회수한다. 예산과 실제 저장소의 용량 제한은 다를 수 있다. 이 후속 기능의 동작·동시 실행·업그레이드 검증은 대기 중이다.

새 임시 작업 폴더는 사용 잠금과 관리 표식을 갖는다. worker가 시작 후/주기적으로 종료된 폴더를 회수하고 실행 중인 변환 프로그램의 폴더는 유지한다. 기존 형식/불명 자료는 [임시 파일 운영 절차](operations.md)를 따른다. 예약·작업 전달·worker 응답 갱신과 임시 정리는 수집/변환 작업 슬롯 밖에서 수행한다. 이 변경의 강제 종료·동시 실행 검증은 대기 중이다.

## 장시간 작업 복구

장시간 작업은 한 번의 실행이 중단되면 같은 작업 ID로 재전달한다. 보관 검사는 저장한 파일/미리보기 위치와 문제 기록부터 이어가며 일시정지·공간 확보 후 재개도 같다. 완료된 실패의 재시도는 전체를 새로 검사한다. 복원 후 미완료 검사도 복원된 파일을 새로 확인한다. 이번 복구 변경은 기능·장시간 실행 검증 대기다.

## 품질 검증과 API 타입

2026-10-10 후속 점검에서 backend 테스트 218개·frontend 테스트 2개, Ruff 정적/형식 검사와 frontend TypeScript 검사/production build가 통과했다. 서버 이름의 HTTP 접속도 작업 요청 키 생성에 지원하며 현재 실패한 실제 우고이라 1개를 복구했다. 이 문서의 2026-10-04 후속 기능별 검증 대기 문구는 당시 상태이며, 최신 자동 회귀 결과·실제 계정 확인 범위·남은 수동 검증은 [검증 기록](validation.md)을 따른다.

```sh
uv run ruff check app tests
uv run ruff format --check app tests
uv run pytest -q
npm --prefix frontend test
npm --prefix frontend run typecheck
npm --prefix frontend run build
```

API 변경 시 아래 산출물을 함께 갱신한다.

```sh
uv run python -m app.cli openapi > docs/openapi.json
npm --prefix frontend run api:generate
```

화면 변경은 [브라우저 검증 절차](validation.md)를 따른다. 현재 자동화한 범위는 backend 도메인·API·worker 테스트이며, 브라우저 E2E는 실제 UI를 조작해 수동 검증했다.

## 백업과 복원

실행 중인 WAL DB 파일 하나만 복사하지 않는다. 대신 `python -m app.cli backup --output DIR --media`로 실행 중에도 일관된 DB 스냅샷과 증분 파일 미러를 만든다. `verify-backup`으로 확인하고, `restore`로 빈 데이터 디렉터리에 복원한다. 쿠키 암호화 키는 포함하지 않으므로 `secrets/credential.key`를 따로 보관한다. Redis는 아카이브 백업 기준이 아니다. 명령과 Docker 예시는 [운영 안내](operations.md)에 있다.

증분 미러는 크기·SHA-256이 맞는 파일만 재사용하고 복사본도 검증 후 확정한다. 출력별 잠금과 비공개 준비 폴더를 사용하며 DB/manifest 준비 후 완료 이름으로 공개한다. 일부 파일을 미러에 보관하지 못하거나 해시 기준이 없으면 완료 여부와 문제 수를 남기고 종료 코드 1을 반환하며 마지막 성공 시각을 갱신하지 않는다. `verify-backup --hash`는 DB 해시를 검사하고 복원은 원본의 DB 해시를 복사 중 항상 비교한다. `restore --verify-hash`는 미러를 먼저 해시 검사하고 기준 없는 과거 아바타도 제외한다. 이 후속 변경의 기능·장애 검증은 일괄 검증 대기다.

복원은 해당 저장소를 쓰는 web·worker·일반 CLI를 종료한 뒤 진행한다. 서비스 수명의 공유 잠금과 복원 독점 잠금으로 동시 사용을 거부하며, 준비 DB에서 파일 복사·마이그레이션·누락/실행 상태 정리를 마친 뒤 최종 DB를 공개한다. 중단 표식이나 준비 DB가 남으면 서비스/일반 CLI를 시작하지 않는다. 표식을 임의로 제거하지 말고 새 빈 대상에 다시 복원한다. 이 후속 변경의 중단·동시 실행 검증은 대기 중이다.

스키마 v1→v4 업그레이드와 기존 데이터 보존, 백업→새 데이터 디렉터리 복원은 자동 테스트로 확인했다. Docker 새 볼륨 복원 훈련과 예약 백업은 아직 검증·구현하지 않았다.
