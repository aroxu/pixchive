# 운영 안내

갱신일: 2026-10-04. 자동 테스트로 확인한 범위와 아직 실제 환경에서 확인하지 않은 범위를 구분해 적는다. 실행 준비는 [실행 안내](README.md)를 따른다.

## 첫 설정과 수집 준비

웹 서버 기본 수신 주소는 `0.0.0.0`이며 접속 주소와 쓰기 허용 출처는 별도다. 여러 접속 주소는 `PIXCHIVE_ALLOWED_ORIGINS`에 정확한 HTTP/HTTPS Origin을 쉼표로 지정한다. Compose는 로컬 `.env`를 읽고 직접 실행할 때는 해당 값을 환경 변수로 불러온다. 설정 변경은 web 재시작으로 반영하며 worker 작업과 쿠키를 지우지 않는다. HTTPS 별칭의 로그인 쿠키도 Secure로 발급한다.

관리자를 처음 생성하면 `/setup`에서 실제 저장 공간·PHPSESSID 저장/연결 검증·다운로드 등급·공개/비공개 범위와 수집 방식을 차례로 준비한다. 기존 관리자도 설정의 **첫 설정 안내**에서 같은 화면을 열 수 있다. 실제 쿠키는 나중에 넣을 수 있으며 연결 검증과 수집은 버튼을 눌렀을 때만 작업으로 요청한다. 안내 화면은 다운로드 정책 불러오기 실패·미저장 변경·저장 중에 첫 수집을 비활성화한다. 지원 범위는 일러스트·만화·우고이라이며 소설은 제외한다. 우고이라 ZIP/타이밍과 재생용 x264 H.264 MP4를 구별한다. 새 안내 화면의 기능·브라우저 검증은 대기 상태다.

## 동기화 방식과 요청량

**일반 동기화**는 선택한 범위의 북마크 목록을 처음부터 끝까지 확인한다. 작품 상세는 새 작품, 목록 행의 지문(제목·작가·페이지 수·수정일·태그)이 바뀐 작품, 원본 보관이 끝나지 않은 작품, 마지막 확인 후 `작품 정보 갱신 기준`이 지난 작품만 다시 받는다. **전체 메타데이터 갱신**은 모든 작품의 상세를 다시 받는다. 두 방식 모두 원본 URL과 로컬 파일이 그대로인 페이지는 다시 내려받지 않는다.

요청 수는 대략 다음과 같다. 목록은 48개마다 로그인 확인 1회와 목록 1회, 작품 상세는 작품마다 2회(상세와 페이지 또는 우고이라 정보)다. 북마크 1만 개라면 일반 동기화의 목록 확인은 약 420회, 전체 갱신은 여기에 약 2만 회가 더해진다. 기본 요청 간격 1초에서는 각각 7분 이상, 5시간 반 이상 걸린다. 이 숫자는 계산값이며 실제 Pixiv 제한이나 안전한 속도를 확인한 결과가 아니다.

요청 간격은 설정의 **예약 동기화** 카드에서 0.5~10초로 바꾼다. 429 응답은 `Retry-After`와 DB에 저장한 대기 시각을 지키고, 같은 계정의 다른 작업도 그 시각까지 시작하지 않는다.

## 예약 동기화

설정에서 예약을 켜고 실행 간격, 수집 범위, 전체 갱신 주기, 작품 정보 갱신 기준, 요청 간격을 저장한다. 판단은 worker가 5초마다 DB 설정을 읽어 수행한다. worker가 꺼져 있던 동안 놓친 실행은 다시 시작할 때 한 번만 실행하고 그때부터 간격을 다시 센다.

- 같은 범위와 요구 방식을 충족하는 수집 작업(일시정지·인증 대기·저장 공간 대기 포함)이 있으면 `합침`으로 기록한다. 전체 작업은 일반 요청도 충족하지만 일반 작업이 전체 요청을 대신하지 않는다. 다른 범위/전체 요청은 별도 대기열에 보존하며 모든 계정 작업은 같은 lease로 하나씩 실행한다. 멈춘 작업을 재개하거나 취소해야 그 작업의 다음 예약이 새 작업을 만든다. 같은 키의 취소가 끝나지 않았으면 종료 후 재요청 안내를 반환한다.
- 쿠키가 없거나 연결 검증이 필요하면 실행하지 않고 사유를 기록한다.
- 선택 범위의 전체 갱신 주기가 지났으면 해당 예약을 전체 갱신으로 만든다. 공개/비공개 시각은 따로 기록하며 두 범위는 더 오래된 시각을 쓴다. 한 범위가 미기록이면 전체 갱신이 필요하다. 이전 공통 시각만 있는 설치에서는 어느 범위가 완료됐는지 추정하지 않고 다시 전체 갱신한다.
- 연결 검증이 성공하면 인증 대기 중이던 수집·다시 받기 작업을 자동으로 대기열에 다시 넣는다.

범위별 갱신 시각은 마지막 페이지의 앞부분/총수 재확인과 메타데이터 기록을 같은 트랜잭션으로 확정했을 때 갱신한다. 정보/북마크 태그 확인 오류가 있으면 기존 시각을 유지한다. 원격 접근 불가와 사용자 수집 제외는 오류와 구별한다. 원본 다운로드/변환 완료 시각이 아니므로 파일 실패/변환 대기가 남을 수 있으며 작업 결과에서 확인한다. 예약 범위 변경 시 새로 선택한 범위의 기록으로 다음 방식을 판단한다. 새 범위/방식 합침·기존 작업 재개·업그레이드 검증은 대기다. 업그레이드는 web/worker를 모두 정지한 뒤 같은 새 버전으로 시작해 새 작업 키와 기록 정책을 함께 적용한다.

## 저장 공간

`PIXCHIVE_MIN_FREE_MB`(기본 1024)는 새 다운로드와 우고이라 변환에 남겨 둘 여유 공간이다. 새 작업은 이 값에 자신과 다른 진행 작업의 예상 공간 예산을 더해 확인한다. 원본 다운로드에는 최대 원본 100 MiB와 여유 8 MiB, 아바타 5 MiB, 미리보기 8 MiB를 잡는다. 우고이라는 프레임 해상도/개수에 따른 PNG 공간과 MP4 출력/저장 복사본 각각 최대 200 MiB 등을 보수적으로 계산한다. 추정치는 실제 파일 크기와 다를 수 있다. 기본 여유 공간보다 남은 공간이 많아도 새 작업의 예산이 부족하면 `저장 공간 대기`로 멈춘다. 이미 받은 원본은 유지된다.

작업의 **필요한 여유 공간 (추정)**은 마지막 검사 시점의 작업 예산·다른 진행 작업의 예산·기본 여유 공간 합이다. **검사 당시 남은 공간**과 **공간 확인 시각**을 함께 확인하고 공간을 확보하거나 다른 작업이 끝난 뒤 **다시 시도**한다. 현재 남은 공간은 설정의 저장소 카드에서 확인한다. 여유 공간이 충분해도 실제 저장소의 용량 제한으로 실패할 수 있으므로 이 경우 저장소 설정도 확인한다. 종료·일시정지/취소 확인·실패·lease 만료 때 예약을 해제하고 재시도 때 다시 계산한다.

설정의 저장소 카드는 역할별 보관 용량, DB 크기, 작업 대기열, 예약 여유 공간과 **진행 작업의 공간 예산**을 보여 준다. 마지막 항목은 실제 파일이 차지한 용량과 구별된 추정값이다. 이 후속 구현의 기능·동시 실행 검증은 일괄 검증 대기다.

## 임시 파일과 worker 유지 작업

새 파일 저장·아바타·우고이라 변환은 `data/tmp/work-{목적}-{임의 ID}`를 사용한다. 정상 종료와 실패/취소 확인 후 폴더를 정리하고, 강제 종료로 남은 폴더는 worker 시작 후 및 매분 최대 50개씩 회수한다. 관리 표식과 실제 사용 잠금을 확인하며 worker 또는 변환 프로그램이 사용 중인 폴더는 유지한다. 원본 저장 경로로 이동한 파일은 기존 보관 기록의 staged 검사를 통해 확정한다.

기존 버전의 개별 임시 파일/`ugoira-...` 폴더나 관리 표식을 확인할 수 없는 자료는 자동 회수하지 않는다. 운영 중 `data/tmp`를 통째로 지우지 말고, 이런 자료를 정리할 때는 모든 worker/변환 프로그램이 종료된 뒤 내용을 확인한다. 개발용 목업/테스트 자료의 최종 정리는 일괄 검증 후 별도로 진행한다. 회수 실패는 `temporary_workspace_cleanup_incomplete`/`temporary_workspace_cleanup_retry`, 불명 항목 수는 `temporary_workspace_cleanup` 로그로 확인한다. 로그에는 임시 파일 이름이나 인증 정보를 넣지 않는다.

예약 판단·outbox 재전달·worker 응답 시각은 수집/변환 작업 슬롯과 독립된 5초 유지 작업으로 갱신한다. 수집·검사·변환 2개가 함께 실행 중이어도 이 유지 작업을 위한 별도 슬롯을 기다리지 않는다. 임시 파일 정리도 별도로 수행한다. Redis 전달 실패/시간 초과는 `worker_dispatch_retry`를 기록하고 DB의 미전달 작업을 다시 시도한다. 이 후속 구현의 강제 종료·동시 사용·슬롯 포화 검증은 일괄 검증 대기다.

## 영상 변환과 작업 조회

우고이라 재생 파일은 GIF 대신 x264 인코딩의 H.264 MP4로 만든다. 원본 ZIP과 프레임 타이밍은 별도로 보존하므로 재생 파일이 손상돼도 다시 변환할 수 있다. 기본값은 CRF 18·medium·yuv420p이며 프레임별 타이밍을 유지하고 faststart를 적용한다. 2026-10-10부터 `-bf 0`으로 B-frame 재정렬을 끄며 가변 프레임 간격에서 컨테이너 길이가 짧게 기록되는 것을 막는다. 압축률은 기존 출력보다 낮아질 수 있으며 원본이나 타이밍을 바꾸지 않는다. FFmpeg에 `libx264`가 없거나 생성 파일의 형식/길이 검증이 실패하면 변환 작업을 실패로 기록하며 GIF로 대신 저장하지 않는다.

설정의 **우고이라 영상 변환**에서 동시 실행 수를 1개(기본) 또는 2개로 저장한다. 더 많은 변환은 CPU·메모리·임시 공간을 더 사용한다. 새 변환을 시작할 때 DB 트랜잭션에서 모든 worker의 유효한 실행 lease를 세므로 여러 worker도 같은 제한을 공유한다. 실행 중·일시정지 중·취소 중인 변환은 종료 확인까지 자리를 차지한다. 제한을 낮춰도 진행 중인 변환은 중단하지 않고 종료될 때까지 다음 시작을 기다린다. 계정별 Pixiv 요청 lease와는 별개다. worker의 동시 작업 한도는 4개이며 계정 작업 1개·보관 검사 1개·변환 최대 2개를 처리할 수 있다.

**작업**에서 종류·상태·실행 방법을 선택하고 과거 기록을 페이지별로 탐색한다. 제목이나 **작업 상세**를 누르면 원본 다운로드 항목 집계와 부모/하위 변환, 모든 상태 변경·문제 항목을 확인한다. 항목 집계는 이미지 페이지 또는 우고이라 원본 묶음 단위이며 실제 디스크 파일 수와 같지 않을 수 있다. 완료·실패·등급 제외·로컬 삭제 제외를 구별한다. 필터와 페이지는 목록 복귀 시 유지한다. 예전 최근 100개 API는 유지하며 화면은 새 페이지 API를 사용한다.

보관 검사는 전체 파일 ID를 메모리에 올리지 않고 시작 시점의 파일 행 범위를 최대 200행씩 읽는다. 진행 중에는 처리 건수를 표시하고 원본 검사 종료 시 정확한 총수를 확정한다. 검사 후 추가한 파일은 다음 검사에서 확인한다.

## 미리보기 다시 생성

일러스트·만화 상세의 관리 영역에서 **미리보기 다시 생성**을 누르면 보관한 첫 페이지로 목록용 WebP를 만든다. PHPSESSID와 다운로드 등급 선택 없이 사용할 수 있으며 앱의 표시 권한은 적용한다. 원본을 다시 내려받거나 바꾸지 않는다. 작업 상태와 **작업 보기**를 확인하고, 멈춘 기존 작업이 반환되면 작업 화면에서 재개한다. 원본 누락/해시 불일치는 먼저 원본 복구가 필요하며 공간 부족은 확보 후 재시도한다. 우고이라 썸네일은 기존 **재생 파일 생성**으로 MP4와 함께 다시 만든다.

스키마 v10은 미리보기의 원본별 연결을 보관한다. 과거 자료는 파일 생성 순서로 관계를 추정하지 않으며 다음 실제 미리보기 생성/보관 검사에서 연결을 채운다. 같은 파생 파일을 여러 원본이 재사용해도 원본은 따로 보존한다. 보관 검사의 미리보기 보완 실패는 문제 항목과 일부 확인 필요로 남긴다. 삭제 요청은 해당 작품의 미리보기 작업을 취소하고 실제 종료를 기다린다. 새 기능·기존 자료 업그레이드/복원·브라우저 검증은 대기다.

## 재개와 공유 변환

작업의 **재개**·**다시 시도**가 같은 범위의 기존 작업에 합쳐지면 안내의 **해당 작업 보기**로 실제 작업을 확인한다. 이때 원래 멈춘 작업의 변환을 별도로 시작하지 않는다. 받아들인 부모 재시도는 멈춘 변환도 재개하고 새 변환이 기존 실패 변환을 대신하면 연결 목록을 새 작업으로 갱신한다. 취소된 변환은 명시적으로 부모를 다시 시도할 때 새 작업으로 요청하며 보관 원본·이전 작업 기록은 유지한다. 이미 로컬 삭제한 원본은 다시 변환하지 않는다. 변환이 중단 중이면 종료 안내에 따라 끝난 뒤 다시 요청한다.

같은 우고이라의 변환을 여러 수집·복구 작업이 함께 사용할 수 있다. 한 부모를 멈추거나 취소해도 다른 진행 작업이 필요한 변환은 계속된다. 다른 부모도 멈춰 있으면 취소 대신 재개할 수 있도록 일시정지한다. 자신이 중단한 변환은 실제 종료 확인 전까지 중단 중으로 표시한다. 변환 작업 자체의 중단/취소는 공유 중인 모든 부모의 완료에 영향을 주므로 상세의 연결 목록을 함께 확인한다. 새 재개·공유 제어·연결 변경 동작의 기능/브라우저 검증은 대기다.

## 장시간 작업과 보관 검사

장시간 작업은 실행 제한이나 worker 종료 후 파일 쓰기·프로세스 종료를 기다리고 같은 작업 ID로 대기열에 돌아간다. 강제 종료는 실행 권한 만료 후 회수되며 이전 Redis 실행 표시가 남아도 새 전달을 사용한다. 진행 기록은 유지하므로 UI 작업 이력에서 중단과 재실행을 확인할 수 있다. 개별 다운로드/변환의 완료 파일과 수집 커서도 기존 복구 규칙을 따른다.

보관 검사의 일시정지/공간 대기 후 재개는 저장한 위치부터 수행한다. 검사 도중 새로 추가한 파일은 다음 검사에서 확인한다. 완료된 실패/부분 결과를 재시도하면 현재 보관 전체를 다시 검사한다. 백업 복원 시 미완료 검사는 이전 위치와 문제 목록을 지우고 복원된 파일을 처음부터 확인하며 완료 작업 이력은 보존한다. 이 후속 변경의 실제 장시간 실행·강제 종료·복원 시나리오는 일괄 검증 대기다.

## 다운로드 등급과 원본 복구

**다운로드할 작품 등급**은 라이브러리 표시와 독립적이다. 기본값은 모든 등급이며 미확인 등급은 전체 연령과 구분한다. 선택하지 않은 등급도 메타데이터는 수집하고 기존 파일은 유지한다. 빈 선택은 메타데이터만 보관한다. 등급을 새로 허용하면 다음 동기화 또는 작품 상세의 **원본 확인 및 다시 받기**로 파일을 받는다. 작업 중 설정 변경은 다음 파일 처리부터 적용하며 파일 수신 후 저장 전에 다시 확인한다. 이미 저장 중인 파일이나 보관된 로컬 원본의 파생 변환은 완료될 수 있다.

**보관 파일 검사**가 발견한 문제는 작업의 **확인할 항목 보기**에서 작품 ID·파일 역할·누락/손상/읽기 실패로 표시한다. 작품 상세의 **원본 확인 및 다시 받기**는 현재 원격 원본만 복구하며 메모·태그와 과거 리비전을 보존한다. 현재 다운로드 등급 허용과 검증된 Pixiv 연결이 필요하다. 원격에서 접근 불가한 작품과 이미 취득한 과거 원본의 재획득은 보장하지 않는다.

다시 받은 내용이 기존 보관 기록의 해시와 일치하면 손상된 바이트를 그 내용으로 교체한다. 원격 원본이 바뀌었으면 새 리비전으로 보관하며 과거 파일은 유지한다. 기록 없는 경로에 다른 파일이 있거나 파일 기록 자체가 불일치하면 덮어쓰지 않고 오류로 남긴다. 보관 검사에서 실패한 파일은 크기가 같다는 이유만으로 재사용하지 않는다. 검사와 복구/삭제는 상태 확정 순서를 조정하므로 큰 파일 검사 중 저장 완료가 잠시 기다릴 수 있다. 이 후속 복구 동작은 아직 기능 검증 대기다.

## 모바일 상세와 정보 펼치기

모바일에서는 이미지/MP4와 제목·작가·보관/변환 상태를 먼저 확인하고 **설명·태그·보관 기록 펼치기**에서 편집·이력/파일·복구/내보내기/삭제를 사용한다. 정보 영역을 접어도 진행 중인 편집 요청을 취소하거나 미저장 메모/별칭을 지우지 않는다. 내부 파일/이력·당시 정보 조회는 정보가 보이는 동안에만 활성화하며 접힌 동안 주기적 조회를 멈춘다. 이미 진행 중인 로컬 API 조회는 완료될 수 있다. 데스크톱은 항상 펼치며 같은 작품의 모바일 펼침 선택을 너비 변경 동안 유지한다. 삭제 확인창이 열린 상태에서 너비를 줄이면 정보도 펼쳐 둔다. 이 모바일 기능과 focus/실제 터치 동작은 검증 대기다.

## 수집 정보와 이전 보관본

작품 상세의 **수집한 작품 정보**는 게시·처음 수집한 시각·수집 당시 작가 이름과 제공된 계정명을 표시한다. **등급 원문 기록**은 출처와 값을 표시하며 필드 누락과 명시적 null을 구별한다. 정수 0/1/2 이외의 값은 등급 미확인이다. 원문 기록이 없는 기존 자료는 다음 메타데이터 갱신으로 기록하며 정규화 등급에서 값을 역산하지 않는다. 계정명이 누락된 응답은 이전에 확인한 계정명을 지우지 않는다.

**보관 파일과 이전 보관본**은 파일 종류별 페이지 조회로 이전 리비전과 파생 파일까지 표시한다. 크기·해상도·SHA-256·최근 확인 상태를 살펴보고 확인 완료 파일을 개별로 내려받는다. 경로 기록은 Pixiv 원본 이미지/우고이라 ZIP 요청 경로, 제공 타이밍, 로컬 미리보기/영상을 구분하며 실제 최고 품질을 검증했다고 해석하지 않는다. 원격 URL/쿠키/서버 절대 경로는 이 목록에 제공하지 않는다. 과거 파일은 유지하고 기본 뷰어/작품 ZIP은 현재 페이지 범위의 최신 ready 원본을 선택한다. 페이지 수가 줄거나 형식이 바뀐 과거 원본은 이전 보관본에서 찾을 수 있다.

## 작가·태그 목록

작가·태그 목록은 **이름순/작품이 많은 순** 정렬과 서버 검색·페이지를 제공한다. 태그의 **태그 출처**로 작품 태그·북마크 태그·로컬 태그를 고른다. 전체 태그 건수는 출처별 카드 수이며 같은 이름이 여러 출처로 나타날 수 있다. 카드의 작품 수는 해당 출처의 고유 작품 수이고 숨긴 등급/수집 제외는 세지 않는다. 새로 만든 미사용 로컬 태그만 0건 카드에 남는다. 이름 변경 화면은 같은 이름의 태그가 있으면 병합을 안내하며 조회 실패/확인 중에는 저장을 기다린다. 미리보기 후 대상이 바뀔 수 있으므로 최종 이름 변경은 그 시점의 대상을 다시 확인한다.

## 원격 변경 이력

작품 상세의 **원격 변경 이력**에서 모든 저장 버전을 페이지별로 찾아 **당시 정보 보기**를 펼친다. 기록 시각은 각 버전을 처음 확인한 시각이고 같은 버전을 다시 확인해도 이력이 늘지 않는다. 과거 작품/북마크 태그와 번역은 별도로 표시한다. 당시 태그가 없는 것과 당시 확인하지 못한 것을 구별한다. 숨긴 등급의 과거 기록은 표시 설정을 허용한 뒤 조회할 수 있고, 읽기 불가 기록 때문에 다른 기록까지 숨기지 않는다. 이전 기록이 손상/숨김이면 변경 비교를 제공하지 않는다. 현재 메모·별칭·로컬 태그는 이 열람으로 바뀌지 않는다.

## 로컬 태그 관리

작품 목록의 **현재 페이지 N개 선택**과 카드별 체크박스는 표시된 작품 ID만 선택한다. **현재 페이지 선택 해제**로 풀 수 있으며 페이지·검색/범위를 바꾸면 초기화한다. 아래 편집 영역은 선택한 ID·이름·추가/제거를 요청 시점에 고정하고 처리 중 선택/입력을 잠근다. 서버는 모든 작품의 표시 권한·수집 제외 여부를 확인한 뒤 로컬 관계만 한 번에 기록한다. 하나라도 접근할 수 없으면 일부만 적용하지 않고 오류를 반환한다. 없는 이름의 제거는 사전 생성 없이 끝나며 반복 추가/제거는 관계를 중복하지 않는다. 새 선택/편집 흐름의 기능 검증은 대기 상태다.

태그 화면에서 원문·제공된 번역으로 검색하고 태그 상세에서 언어·출처와 출처별 작품 수를 확인한다. 상세의 전체 수는 작품 중복을 제거하므로 출처별 수의 합과 다를 수 있다. 태그 이름을 바꾸어도 ID 기반 상세의 작품 연결은 유지된다. 태그 화면에서 빈 로컬 태그를 만들 수 있다. 이름 변경은 원격 작품 태그·북마크 태그·Pixiv 번역과 공유되지 않은 로컬 전용 태그에만 가능하다. 이미 있는 이름으로 바꾸면 그 태그로 로컬 관계만 합치고 중복은 하나로 유지한다. 대상 태그의 원격 관계를 바꾸지 않는다.

2026-10-04의 위 기능은 구현 후 일괄 테스트 대기 상태다.

## 로컬 삭제와 수집 제외

작품 상세의 **로컬에서 삭제**는 삭제할 파일 수와 용량을 보여 준 뒤 확인을 받는다. 확인하면 tombstone을 먼저 기록해 목록·검색·미디어 응답에서 바로 숨기고, worker가 원본·우고이라 ZIP/타이밍·미리보기·재생 파일을 영구 삭제한다. 휴지통은 없다. 삭제 작업은 멈추거나 취소할 수 없고, 실패하면 다시 시도한다. 작품 정보·로컬 태그·메모는 수집 제외 목록에 남고 Pixiv 북마크는 바꾸지 않는다.

설정의 **수집 제외 목록**에서 제외를 해제한다.

- **제외 해제 후 다시 받기**: Pixiv 연결이 필요하다. 작품 상세를 다시 받고 현재 원본을 내려받는 작업을 만든다.
- **제외만 해제**: 작품 정보를 다시 표시한다. 북마크에 남아 있으면 다음 동기화가 원본을 받는다.

## 내보내기

- 작품 상세의 **파일·정보 내보내기**: `metadata.json`과 현재 원본을 ZIP으로 받는다. 우고이라는 원본 ZIP·타이밍과 준비된 재생 파일을 포함한다.
- 설정의 **전체 메타데이터 내보내기**: 표시 설정과 관계없이 모든 보관 작품의 정보·세 출처 태그·메모·북마크 상태·파일 해시 목록과 수집 제외 기록을 JSON으로 받는다. 원본 파일과 쿠키는 포함하지 않는다.

둘 다 앱 로그인이 필요하다. 작품 ZIP은 그 작품의 등급 표시 제한도 따른다.

작품 ZIP은 시작 전 포함 파일의 존재/크기를 확인하고 전송 중 SHA-256과 실제 크기를 검증한다. 파일이 중간에 삭제/변경되거나 읽기에 실패하면 정상 ZIP 완료로 처리하지 않고 다운로드를 중단한다. 중단된 ZIP은 사용하지 말고 **보관 파일 검사** 또는 **원본 확인 및 다시 받기**로 파일을 확인한 후 다시 내보낸다. 내보내기는 실행 중 DB/파일 전체의 일관된 백업을 대신하지 않는다.

## 백업

`backup` 명령은 SQLite 온라인 백업 API로 실행 중에도 일관된 DB 스냅샷을 만든다. web과 worker를 멈출 필요가 없다.

```text
OUTPUT/
  pixchive-backup-20261002T070000Z/
    pixchive.db       # 일관된 스냅샷 (journal_mode=DELETE)
    manifest.json     # 스키마 버전, 작품·파일 수, 복사 결과
  media-mirror/       # --media 사용 시: 스냅샷이 참조하는 파일
    media/...
    avatars/...
```

`--media`는 스냅샷이 참조하는 원본·파생 파일·작가 아바타를 `media-mirror`로 복사한다. 원본과 기존 미러의 크기·SHA-256을 확인하고 맞는 미러만 건너뛴다. 같은 크기의 손상 파일도 다시 복사하며, 복사본을 읽어 검증한 뒤 원자적으로 교체한다. 미러에서 과거 파일을 지우지 않으므로 이전 스냅샷도 복원할 수 있다. 해시 검사에는 파일 전체 읽기가 필요하므로 이전의 크기만 비교하던 백업보다 디스크 읽기량이 많다. 쿠키 암호화 키는 백업에 들어가지 않는다. `secrets/credential.key`를 다른 안전한 위치에 따로 보관한다.

같은 출력으로 실행한 백업은 `.backup.lock`으로 순서대로 처리한다. DB·manifest는 비공개 `.pixchive-backup-*` 준비 폴더에서 동기화한 뒤 완료 이름으로 공개한다. 일반 오류는 이번 준비 폴더를 제거하지만 강제 종료로 남은 숨김 폴더나 `.partial` 복사본은 완료 백업이 아니다. 해당 출력의 백업이 모두 종료된 뒤 내용을 확인하고 정리한다. 미러의 정상 파일과 완료 스냅샷은 함께 보존한다.

결과의 `media.missing_in_source`·`mismatched_in_source`는 원본 문제 수, `unavailable`은 미러에 유효하게 보관하지 못한 수다. 원본에 문제가 있어도 기존 미러가 DB 해시와 맞으면 그 미러를 유지하므로 두 수는 다를 수 있다. 해시 기준 없는 과거 아바타는 복사해 보존하되 `unverifiable`로 센다. 미보관/해시 기준 없음이 하나라도 있으면 `media.complete=false`로 진단용 DB 스냅샷과 결과를 남기고 CLI 종료 코드 1을 반환하며 마지막 성공 시각을 갱신하지 않는다. `--media`를 생략한 DB 전용 백업은 파일 완료 여부가 null이다. 잘못된 참조·파일 경계·권한/공간 오류는 성공으로 처리하지 않고 종료 코드 2로 알린다.

로컬 실행:

```sh
uv run python -m app.cli backup --output /mnt/backup/pixchive --media
uv run python -m app.cli verify-backup /mnt/backup/pixchive/pixchive-backup-20261002T070000Z --hash
```

Docker Compose에서는 같은 데이터 볼륨을 쓰는 일회성 컨테이너로 실행한다. 서비스 포트는 열리지 않는다. 컨테이너가 root로 실행되므로 백업 파일 소유자도 root다.

```sh
mkdir -p /mnt/backup/pixchive
docker compose run --rm --no-deps -v /mnt/backup/pixchive:/backup web \
  python -m app.cli backup --output /backup --media
```

`verify-backup`은 스냅샷 무결성·관계·스키마 이력과 미러 파일의 존재·크기를 확인하고, `--hash`를 주면 SHA-256까지 비교한다. 현재 아바타는 해시 파일명을 기준으로 검사한다. 과거 해시 없는 아바타 경로는 `--hash`에서 `unverifiable`로 구별한다. missing/mismatched/unverifiable의 전체 수와 각 최대 20개 경로를 출력하며 문제가 있으면 종료 코드 1을 반환한다. 마지막 성공 백업 시각은 설정의 백업 카드에 표시된다.

## 복원

복원은 **빈 데이터 디렉터리**에만 한다. 기존 DB나 원본이 있으면 거부하며 실행 중인 아카이브에 합치지 않는다.

해당 저장소의 web·worker와 쓰기 CLI를 모두 종료한 뒤 실행한다. 서비스와 일반 CLI는 `.data-access.lock`의 공유 잠금을 유지하며 복원은 독점 잠금을 요구한다. 사용 중이면 기다리며 덮어쓰지 않고 `data_in_use`와 종료 코드 2를 반환한다. 잠금 파일은 사용 중에 삭제하지 않는다. 이전 버전 프로세스에는 이 잠금이 없으므로 업그레이드 전에 반드시 함께 정지한다.

```sh
PIXCHIVE_DATA_DIR=/srv/pixchive-new/data uv run python -m app.cli restore \
  --from /mnt/backup/pixchive/pixchive-backup-20261002T070000Z --verify-hash
```

`--media-root`를 생략하면 스냅샷 옆의 `media-mirror`를 사용한다. 복원은 스냅샷 무결성과 스키마 버전을 확인하고 시작 표식 `.restore-incomplete`를 영속화한 뒤 준비 DB `pixchive.db.restoring`과 참조 파일을 복사한다. 준비 DB에서 마이그레이션과 누락/실행 상태 정리를 수행하고 WAL/저널·DB 검사/동기화까지 마친 뒤 최종 `pixchive.db`를 공개하고 표식을 제거한다. 결과의 `restored_schema_version`은 적용된 스키마 버전이다. 미러에 없거나 크기·해시가 다른 파일은 `missing`으로 표시하고 해당 작품의 보관 상태를 다시 계산한다. Pixiv에 연결되어 있으면 다음 동기화가 보관이 끝나지 않은 작품의 원본을 다시 받는다. 실행 중이던 작업의 lease는 버리며 대기 작업은 worker가 다시 실행한다.

원본의 DB 해시와 현재 아바타의 파일명 해시는 복사 중 항상 비교한다. 복사 중 크기/상태 변화와 임시 복사본 자체의 해시도 확인하고 확정 전 실패한 파일은 누락으로 남긴다. `--verify-hash`는 미러를 먼저 해시 검사하고 해시 기준 없는 과거 아바타도 누락으로 처리해 연결을 비운다. 옵션이 없으면 과거 아바타를 복사하되 `unverified_avatar_count`와 경로로 구별한다. DB·WAL/SHM/journal 잔존 파일, 미디어 폴더의 심볼릭 링크나 기존 자료가 있는 대상은 거부한다. 복원 도중 전체 프로세스가 중단된 디렉터리는 완성된 설치로 사용하지 말고 별도 빈 디렉터리에 다시 복원한다.

복원한 데이터와 같은 `credential.key`를 `PIXCHIVE_KEY_FILE` 위치에 둔 뒤 web과 worker를 시작한다. 키가 없으면 저장된 쿠키를 읽을 수 없으므로 PHPSESSID를 다시 등록한다. 앱 관리자 계정과 로컬 정리는 DB에 들어 있어 그대로 복원된다.

복원이 실패/중단되어 표식이나 준비 DB/보조 파일이 남으면 서비스 시작과 init/migrate/backup/seed 명령도 `restore_incomplete`로 거부한다. 표식만 지워 실행하지 않는다. 중단된 대상과 원본 백업은 보존하고 새 빈 디렉터리/볼륨에 다시 복원한다. 현재 같은 대상의 복원 이어받기는 지원하지 않는다. 정상 결과가 누락 파일을 포함하더라도 그 상태를 DB에 기록하고 나머지 자료의 준비를 끝낸 뒤에만 서비스를 시작할 수 있게 한다. 이 후속 경계의 강제 종료·동시 실행 검증은 대기 상태다.

Docker의 새 설치에서는 서비스를 시작하기 전에 빈 볼륨으로 복원한다.

```sh
docker compose run --rm --no-deps -v /mnt/backup/pixchive:/backup:ro web \
  python -m app.cli restore --from /backup/pixchive-backup-20261002T070000Z
docker compose up -d --no-build
```

2026-10-02 시점의 새 데이터 디렉터리 복원·미러 증분 복사·누락 파일 표시·비어 있지 않은 대상 거부는 자동 테스트로 확인했다. 2026-10-04의 해시 기반 재사용·복사 검증·출력 잠금/완료 공개·불완전 결과 처리·복원 시작 표식/준비 DB/수명 잠금·중단 후 시작 차단은 구현 후 일괄 검증 대기다. Docker 볼륨 복원 훈련과 대용량 미러 복사 시간도 아직 실제로 확인하지 않았다.

## 업그레이드

1. 백업을 만들고 `verify-backup`으로 확인한다.
2. web과 worker를 모두 정지한다.
3. 새 버전을 빌드하고 시작한다. 마이그레이션은 시작할 때 적용된다.

스키마 v4는 작품 정보 확인 시각, 목록 지문, 작업 방식·출처·집계, 삭제 기록 상태, 작가 아바타 컬럼을 추가한다. 기존 작품의 확인 시각은 마지막 원격 스냅샷 시각으로 채운다. 기존 수집 작업은 전체 갱신으로 표시된다. 업그레이드 후 첫 일반 동기화는 기존 작품의 목록 지문을 기록하며, 제목·작가·페이지 수가 다른 작품만 상세를 다시 받는다.

스키마 v5는 로컬 태그 카탈로그 표시와 등급 다운로드 제외 집계, 작업별 보관 검사 문제 기록을 추가한다. 기존 local 관계는 카탈로그로 이관하고 다운로드 설정이 없던 설치는 모든 등급 다운로드를 유지한다. v5 마이그레이션·병합·복구의 기능 검증은 일괄 검증 단계에 남아 있다.

스키마 v6는 작업의 최신순/상태/종류 이력과 상태 변경 기록용 조회 인덱스를 추가하며 기존 작업·파일·자격 증명 행은 변경하지 않는다. 기존 DB 업그레이드와 새 작업 화면은 일괄 기능 검증 대기다.

스키마 v7은 작가 계정명·등급 원문·다운로드 항목과 파일의 수집 경로 컬럼 및 파일 종류 조회 인덱스를 추가한다. 기존 데이터의 새 컬럼은 null로 유지하고 실제 확인 없이 역산하지 않는다. 메타데이터 포맷 v2의 전체 JSON은 이전/파생 파일을 포함한 상대 경로·상태·수집 경로를 나열한다. 작품 ZIP의 metadata.json은 그 ZIP에 포함한 최신 파일 목록을 사용한다. 파일 바이트/쿠키/키는 전체 메타데이터 JSON에 포함하지 않는다.

스키마 v8은 원격 작품 정보 이력의 페이지 조회용 정렬 인덱스만 추가한다. 저장된 스냅샷·현재 작품 정보·원본·관계·자격 증명 행은 변경하지 않는다. 기존 데이터 업그레이드와 새 이력/내보내기/화면 복구의 기능 검증은 일괄 검증 단계에 남아 있다.

스키마 v9는 작업의 마지막 공간 확인 값(null 기본값)과 공용 공간 예약 표를 추가한다. 기존 작품·파일·작업·자격 증명은 유지한다. 새 설치로 복원하면 이전 실행의 예약과 예전 볼륨의 공간 확인 값은 지우고 실행할 때 다시 계산한다. 이전 버전의 web·worker를 함께 정지한 뒤 새 버전을 시작한다. 기존 자료의 업그레이드·예약 회수·복원 검증은 일괄 검증 대기다.

## 로그와 작업 기록

web과 worker의 로그 핸들러에 마스킹 필터를 붙인다. PHPSESSID 값, Cookie 값, 쿠키 형식 문자열, 암호화된 자격 증명, 앱 세션 쿠키를 `[redacted]`로 바꾼다. 이 필터는 보조 장치이며 코드는 처음부터 쿠키·URL·원격 오류 원문을 로그와 작업 결과에 넣지 않는다. Pixiv 요청은 로그를 끈 별도 자식 프로세스가 수행한다. 작업 화면의 **작업 기록**은 상태 변경 시각과 오류 코드만 보여 준다.
